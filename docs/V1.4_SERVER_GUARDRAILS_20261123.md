## Firebase Auth reset deployment / acceptance

1. Use a trusted Firebase administrator and correct project `e-report-sags`; verify billing/Functions availability and who is allowed to deploy. Do **not** place service account JSON in GitHub or chat.
2. Deploy specifically the callable (example from an authenticated Firebase CLI environment): `firebase deploy --only functions:adminResetAuthPassword --project e-report-sags`. The repo's `firebase/functions` directory contains dependencies; configure Firebase CLI project/codebase as needed without blindly deploying the retention scheduler. **Do not run a global `functions` deploy** until the scheduler and other exports are reviewed.
3. Verify a known active AD invoking reset for a dedicated **test** Firebase Auth user; check Auth login using the one-time password, `users/{uid}.mustChangePassword=true`, and actual forced password change.
4. Negative-test ordinary DH/CBTT/PVHK users, deleted/inactive users, self-reset and mismatched Firebase/Firestore email. A button click alone is not backend verification.
5. Check Cloud Functions logs for exceptions, with no plaintext password in logs. Never show a success toast unless callable returned `{ok:true,uid:targetUid}`.

## Firebase retention 24h activation (strict order)

1. Independently archive Firestore + RTDB and test restoring representative flight, roster, PDF/photo and radio records to a **separate isolated environment**.
2. Provision least-privilege Firestore/RTDB access with GitHub Actions secrets/Workload Identity as documented in `docs/flight-retention-48h.md`.
3. Keep GitHub variable `SAGS_RETENTION_DELETE_ENABLED` **absent or false**. Run the retention workflow with `dry_run=true`; inspect eligible counts and check whether Door Close timestamps and final documents are correctly grouped.
4. Review 24h coverage, exclusions and proof of restore with AD. Only then set `SAGS_RETENTION_DELETE_ENABLED=true` for intentionally authorized apply runs. The manual workflow still defaults to dry-run.
5. Observe each scheduled execution and errors. Rollback the worker/variable if abnormal; reversing a code commit **cannot restore deleted data**.

## Supabase standby activation

Follow `docs/supabase-standby-setup-20261117.md` and require a complete dry-run, a verified snapshot of all namespaces, checksums, private evidence restore, and an isolated restore drill before enabling periodic replication. Keep Supabase writes/failover disabled.
